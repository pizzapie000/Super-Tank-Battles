Original investigation — retained for context

The following findings and proposed next steps describe the original baseline. The production updates above supersede its implementation status.

The strongest confirmed cause is repeated rebuilding of tank artwork. Slow frames trigger extra physics updates, and each update regenerates artwork that may be replaced again before the screen is drawn.

Best next fix: refresh tank artwork once per displayed frame, then cache the static pieces. In two real-time stress runs without detailed script timers, the scheduling prototype reduced median frame time from 54–66 ms to 29–32 ms. Scenery and occasional AI bursts still need attention.

This investigation added repeatable profiling tools and tested variants in isolated project copies. Production gameplay scripts, edited mission layouts, saved progress, controller assignments and Wii calibration were preserved. The prototype is evidence for a fix; it has not been installed into normal gameplay or the standalone app.

1. The redraw feedback loop

scripts/tank.gd:76 requests new drawing commands on every physics tick. Campaign enemies also request them from scripts/story/story_enemy.gd:40 on every display update. With one physics tick per displayed frame, 13 enemies execute their drawing callback 26 times per frame. The four-player encounter has 20 enemies and executes it 40 times.

Godot flushes deferred work between physics updates. A frame that needs multiple physics ticks can therefore rebuild the same tank several times before presenting it. The final real-time counter run measured:

The render-once experiment suppresses the original redraw requests in a temporary copy and requests fresh artwork from the latest tank state once per displayed frame. Physics, steering, aiming logic, bullets and enemies continue running. The measured improvement below was repeated without function-timing wrappers:

2. Generating tank art costs more than its final draw count suggests

These cases use the same instrumented project, stable cover, two players, 13 enemies and two runs of 300 measured frames. Removing only the extra enemy idle redraw reduces median work from about 35.4 to 29.7 ms. Freezing the existing tank drawing commands reduces it to about 19.9 ms while retaining roughly the same final drawing-call count.

The frozen-art case is a diagnostic: tank positions still change, but turret/tread/recoil artwork stops refreshing. It must not be shipped as an optimization. Its value is separating the cost of rebuilding command lists and graphics resources from replaying them. The shared tank-art functions generate numerous antialiased lines, arcs, polygons and arrays. Native CPU samples also show OpenGL drawing, buffer updates and graphics-driver work.

The four-player fixed-step test supports the same direction: suppressing the extra enemy redraw reduced median work from 51.46 to 40.64 ms, with 4,952 drawing calls in both cases. This was one run per variant, not a repeated estimate.

Godot normally caches custom drawing commands until queue_redraw() invalidates them. Caching the chassis, armor and fixed track details while rotating or moving separate turret/barrel components would preserve the art and avoid reconstructing everything. The engine documentation explains this drawing cache.

Two runs per case, 300 measured frames each, no detailed function timers. The masks act on the rendering server only: tanks, bullets, collision shapes, navigation and scene visibility properties remain active. Hiding world art or tank art saves substantial work. Trees and solid props both contribute; removing the HUD, tread impressions or projectile art has little or inconsistent benefit in this fixture.

These reductions overlap and must not be added together. Mines naturally broke one cover piece in most runs; one baseline retained it. The later drawing experiments locked cover to remove that source of variation. Static trees and barricades already cache their script drawing commands: their remaining cost is submitting and drawing the cached detail, not regenerating those scripts every frame.

OpenGL viewport CPU rendering time was roughly 17–21 ms in representative full-scene tests. A warmed native sample showed graphics submission and buffer operations on the CPU. Godot documents that rendering can be limited by CPU driver work and drawing-call overhead. This supports batching or baking static scenery detail while preserving collision and foliage cover.

Script timings come from nested timers in two fixed-step baseline runs. Self time excludes instrumented child functions; individual maximum call times are inclusive and should not be added to frame totals. Timers themselves add overhead, so these absolute figures belong to this instrumented set.

Shot planning averages about 0.49 ms per fixed frame but sometimes takes almost 9 ms in one call. A path search can approach 7 ms. In each 300-frame run, 21 frame tags accumulated more than 3 ms of combined shot-planning and path-search work. Those frames had median intervals of 42.3–43.3 ms, compared with 34.9–35.4 ms for the other frames. This is evidence of a secondary stutter source; some long frames had little planning work.

The Green-tank battery was lighter in the separate two-player test: median 19.22 ms, 95th percentile 22.52 ms, eight enemies and 1,433 drawing calls. Shot planning averaged 0.18 ms per frame, with a longest call of 5.70 ms. It does not explain the dense forest's whole slowdown. Shell interception averaged about 0.10 ms in the two-player forest and 0.14 ms with four players, so it is not the first target.

5. Checks against misleading conclusions

  • Pixel resolution: reducing the rendered texture from 1037×648 to 260×162 did not improve the stable-geometry baseline (31.41 versus 34.27 ms; one run each, same 3,875 drawing calls). This argues against pixel fill being the main limit. It does not prove the GPU has no cost.
  • Renderer: normal OpenGL and Metal pilots were similar overall (33.08 and 32.56 ms). Changing the renderer is not a demonstrated cure. Their CPU viewport timers differ and must not be treated as the entire frame.
  • Window occlusion: macOS sometimes stopped drawing hidden profiling windows. Those trials were discarded. Accepted cases verify about one actual render per measured frame. An explicit GL presentation path matched a normal baseline closely (33.31 versus 33.08 ms) and made comparisons repeatable.
  • Metal diagnostic caveat: forced drawing plus pending resource processing produced two render passes per frame. Those timings were rejected; the tool now disallows that combination.
  • Unavailable GPU time: GPU timer queries returned zero under both renderers. They are marked unavailable, not interpreted as zero GPU work. Full Instruments/Metal GPU tracing is not installed on this Mac; the native Godot binary also lacks full internal symbols. Viewport CPU timing covers rendering operations, not every script and physics cost.
  • Hardware state: thermal state was nominal and Low Power Mode was off when checked. The sampled game used about 521 MB physical footprint. These observations do not suggest thermal throttling or memory exhaustion as the main cause.

6. Fix order supported by the evidence

  1. Move tank visual refresh out of the repeated physics path. Request it once per display update after the current visual state is ready. Keep physics frequency and collision behavior unchanged. Test paused, dormant and damaged tanks, invisibility, powerup flashing, recoil, turret alignment and White-tank tracks.
  2. Cache stable tank components. Keep chassis/armor/static tread geometry, and update only moving components. Preserve the current vibrant colors, details, tread spacing and assembly sequence. Menu tanks and cutscene assembly share TankArt and need visual checks.
  3. Reduce scenery submission cost. Try texture-backed or batched tree/prop detail and terrain chunks. Preserve canopy layering, tank/bullet concealment, mine-breakable walls, ricochet geometry and level editability. Measure each change with the same workload.
  4. Smooth the remaining AI bursts. Budget or spread expensive path/ricochet requests, cache safe reusable results and invalidate them when cover, mines or targets change. Check Green-tank self-safety and bank-shot behavior before accepting any change.

After each change, compare real-time frame-time percentiles and fixed-step work with two- and four-player encounters, then verify the full game and a release export. These stress results do not promise 60 FPS. Wii input was replaced with a repeatable driver during profiling; a physical two-remote playthrough remains a separate end-to-end check.

How this was measured

Apple M1 Max, macOS 27, Godot 4.7.1 stable. Separate game processes launched outside the editor debugger, Compatibility/OpenGL by default, V-Sync disabled, a 1152×720 visible window and dummy audio. The editor was left open. Forest 3 (checkpoint index 8, “The Overgrown Crossroads”) used two players and 13 enemies, or four players and 20 enemies. Invulnerable test players drive and continuously fire level-III weapons; extra enemy armor keeps combat going. This deliberately sustains a demanding battle.

Most tests advance one fixed 1/60-second simulation step per process frame and report wall-clock work, not normal-play FPS. The final real-time tests omit fixed FPS so normal physics catch-up is included. Modes and repeats are shuffled with seed 143 and run sequentially. No native sampling runs contribute to speed comparisons. The process/physics performance monitors are saved as recent peaks, not mislabelled as exclusive per-frame costs; the matching engine source shows deferred flushes and how those monitors are updated.

Ranges in tables are the minimum and maximum run medians (or run percentiles in the explicitly labelled column), not statistical confidence intervals. Baselines from different fixture/timer sets are kept separate. This establishes specific causes on this machine rather than an exhaustive profile of every level or a release-build benchmark.

Reproduce and inspect

The reusable runner is tools/profile_battle.py. It saves raw frames and metadata, validates render coverage and keeps instrumented code in a temporary copy. Saves are disabled and control assignments are replaced only in memory. Use a new output folder for each run:

python3 tools/profile_battle.py --force-render --repeats 2   --output builds/profiling/render-check

python3 tools/profile_battle.py --instrument --force-render --stable-geometry   --modes baseline single_enemy_redraw freeze_tank_art --repeats 2   --output builds/profiling/draw-check

python3 tools/profile_battle.py --redraw-only --force-render --stable-geometry   --modes baseline render_once --frames 1200 --real-time-seconds 5 --repeats 2   --output builds/profiling/real-time-check

Checkpoint indices are 0–19; add --checkpoint 11 for the Ricochet Battery or --players 4 for a four-player crew. The default Godot executable is ~/Downloads/Godot.app/Contents/MacOS/Godot; override with --godot. Keep windows visible. --sample --frames 600 captures the warmed benchmark process only; sampled timings should not be used for speed claims.
